# 弹幕翻译改造规划

## 目标

在现有 Kiwi Browser Dev 的 Gemini 页面翻译基础上，增加面向直播间评论/弹幕的实时翻译能力。目标不是无条件翻译所有弹幕，而是在高频直播场景中保证浏览器不卡顿、翻译结果尽快出现，并且在刷屏时自动降级。

核心体验目标：

- 普通直播间：新增评论尽量自动翻译，原文可见，译文异步补上。
- 中高频直播间：按批次翻译，减少 API 调用次数，保持 UI 流畅。
- 极端刷屏：只翻译高价值评论或显示热点摘要，避免队列无限堆积。
- 失败/超时：不阻塞页面，保留原文，状态栏提示失败数量或高峰模式。

## 当前代码基线

当前项目是 apktool 反编译工程，已有 Gemini 翻译改动，主要入口如下：

- `smali/org/chromium/chrome/browser/translate/GoogleAiTranslateHelper.smali`
  - `a(Tab)`：用户主动点击浏览器菜单“翻译”时调用，会检查 Gemini Key，注入脚本并强制显示 UI。
  - `c(Tab)`：Tab/WebContents 生命周期中自动调用，有 Key 时静默注入脚本。
  - `f(String)`：当前实际使用的新版注入脚本，版本号 `7`。
  - `b(String)`：旧版注入脚本，版本号 `4`，已包含批量 JSON 翻译、并发处理、加载态插入等逻辑，可作为弹幕批处理改造参考。
- `smali/org/chromium/chrome/browser/app/ChromeActivity.smali`
  - 菜单翻译动作已被接到 `GoogleAiTranslateHelper.a(Tab)`。
- `smali/org/chromium/chrome/browser/tab/TabImpl.smali`
  - `Z()` 里调用 `GoogleAiTranslateHelper.c(Tab)`，用于页面生命周期自动注入。
- `res/xml/translate_preferences.xml`
  - 已有 `google_ai_translate_api_key` 设置项。
- `README_googleai_changes.txt`
  - 记录了现有 Gemini 页面翻译行为，包括抖音/快手直播页处理。

已有能力：

- Gemini Key 不内置，需要用户在设置里保存。
- 页面中注入浮动翻译面板。
- 使用 `MutationObserver` 扫描新增文本。
- 针对抖音/快手直播页识别右侧评论，隐藏横向弹幕、视频、音频。
- 跳过昵称，只翻译评论内容。

当前不足：

- 新版脚本更偏逐条翻译，刷屏时 API 调用次数会变高。
- 没有明确的队列上限、丢弃策略、超时策略和高峰模式。
- 直播评论识别规则较粗，主要依赖类名、位置和 DOM 文本。
- 直接替换原文会影响用户回看原文，弹幕场景更适合原文下方补译文。
- 没有弹幕速率统计，无法根据压力动态切换批量大小或降级模式。

## 推荐架构

继续采用“页面 JS 注入 + Gemini API”的轻量方案，先不引入 Android 原生 WebSocket 网关。原因是当前仓库已有完整注入链，直接改 `GoogleAiTranslateHelper.smali` 的脚本风险最低。

建议拆成以下逻辑层：

```text
WebContents 注入入口
  -> 直播页识别器
  -> 评论/弹幕 DOM 采集器
  -> 过滤器
  -> 去重缓存
  -> 有界队列
  -> 批处理调度器
  -> Gemini 批量翻译
  -> 译文回填器
  -> 高峰降级/状态 UI
```

核心原则：

- 采集和翻译解耦：弹幕先进入队列，翻译异步处理。
- 批量调用：低频等待超时，高频凑满即发。
- 有界资源：队列、缓存、并发、请求时长都必须有上限。
- 可降级：高峰时减少翻译量，不牺牲页面流畅度。
- 可回退：保留原文，不破坏直播间 DOM 主内容。

## 弹幕采集策略

第一阶段不抓平台内部 WebSocket 包，先通过 DOM 采集新增评论。这样兼容性更好，也不需要处理平台签名、压缩、加密或协议变化。

采集来源：

- `MutationObserver` 监听 `childList` 和 `characterData`。
- 优先扫描直播评论容器，而不是全页面。
- 对抖音、快手、YouTube、TikTok 等站点分别维护选择器/启发式规则。

评论容器识别优先级：

1. 平台专用选择器或类名命中。
2. 含 `comment/chat/message/webcast/msg/room/live` 的祖先节点。
3. 位置启发式：右侧或底部评论区，宽度较窄，单条高度较小。
4. 排除横向飘屏弹幕：类名含 `danmu/danmaku/barrage/bullet`、动画/transform 明显移动、覆盖在视频区域上。

每条弹幕数据结构建议：

```js
{
  id,
  node,
  sourceText,
  normalizedText,
  nickname,
  prefix,
  platform,
  createdAt,
  priority,
  retries,
  key
}
```

## 过滤和去重

进入翻译队列前先过滤，减少无意义 API 请求。

过滤规则：

- 纯数字、纯标点、纯表情跳过。
- 过短内容跳过，例如 1 个字符或无语义重复词。
- URL、商品链接、时间戳跳过。
- 已经是目标语言且无外语字符时跳过。
- 同一文本短时间重复出现时复用缓存。
- 同一节点已经处理过时跳过。
- 同一用户连续刷屏时降低优先级。

缓存策略：

- Key：`targetLang + normalizedText`。
- 内存缓存上限：建议 300-800 条。
- 短期 TTL：建议 5-15 分钟。
- 命中缓存时直接回填译文，不进入 API 队列。

本地快翻词库：

- 可内置少量高频短句，例如 `666`、`哈哈哈`、`笑死`、`多少钱`、`听不到`、`卡了`。
- 第一阶段可以只做过滤，第二阶段再加本地快翻。

## 批处理调度

用户提到的“5 条一组 + 超时发送”适合作为默认策略。

推荐参数：

```text
普通模式：
  batchSize = 5
  flushTimeout = 500ms
  maxConcurrent = 2
  requestTimeout = 2500ms
  maxQueueSize = 120

高频模式：
  batchSize = 8-12
  flushTimeout = 800ms
  maxConcurrent = 2
  requestTimeout = 3000ms
  maxQueueSize = 200

极端模式：
  batchSize = 10-15
  只翻译 P0/P1 优先级
  普通弹幕抽样或聚合
```

触发逻辑：

```text
队列达到 batchSize -> 立即发送
队列未满但超过 flushTimeout -> 发送当前批次，即使只有 1 条
请求超过 requestTimeout -> 标记失败或稍后重试，不阻塞队列
队列超过 maxQueueSize -> 丢弃低优先级旧弹幕
```

旧版 `b(String)` 中已有 `takeBatch()`、`callBatch()`、JSON 映射回填和并发 Promise，可把这些思路迁移到当前 `f(String)` 版本。

## 优先级和高峰降级

建议为每条弹幕计算优先级：

```text
P0：付费消息、管理员、主播点名、系统高亮
P1：问句、较长句子、含关键词、非重复文本
P2：普通评论
P3：短句、重复、刷屏、低信息密度文本
```

速率统计：

- 维护最近 5 秒新增弹幕数。
- 低于 10 条/秒：普通模式。
- 10-50 条/秒：高频模式。
- 高于 50 条/秒：极端模式。

极端模式动作：

- 不再翻译 P3。
- P2 只抽样翻译。
- P0/P1 继续优先翻译。
- 状态栏显示“高峰模式，仅翻译重点弹幕”。
- 后续可做热点摘要，例如“多人在问价格 x 43”。

## Gemini 调用格式

批量翻译应强制 JSON 输出，便于回填对应节点。

请求内容示例：

```text
目标语言: 中文
请翻译以下直播间评论，只返回 JSON 对象，key 为编号，value 为译文。
不要解释，不要 Markdown，不要翻译昵称。

1: how much is this?
2: ship to Canada?
3: the sound is too low
```

期望返回：

```json
{
  "1": "这个多少钱？",
  "2": "可以发加拿大吗？",
  "3": "声音太小了"
}
```

失败处理：

- JSON 解析失败时尝试截取 `{...}` 再解析。
- 单条缺失时只跳过该条，不让整批失败。
- API 失败时最多重试 1 次，换备用模型。
- 超时后回填失败态或保持原文，不继续占用并发。

模型策略：

- 默认优先低延迟模型。
- 保留备用模型。
- 后续如果成本或速度压力大，可把弹幕翻译接口切到自建网关，由网关再调模型。

## UI 展示

弹幕场景推荐“原文 + 下方译文”，避免替换原文导致上下文丢失。

显示策略：

- 普通评论：在原文后插入一个小号蓝色译文块。
- 正在翻译：显示轻量 spinner 或不显示，避免刷屏时大量动画拖慢页面。
- 失败：不必每条都显示“翻译失败”，高频时只在状态栏累计失败数。
- 缓存命中：立即插入译文，不显示加载态。
- 高峰模式：顶部状态栏提示当前模式和已丢弃数量。

状态栏建议字段：

```text
已译 128 / 队列 23 / 缓存 41 / 丢弃 96 / 高频模式
```

## 设置项规划

第一阶段可以不新增 Android 设置，只使用当前 Gemini Key 和目标语言本地存储。

第二阶段再考虑新增：

- 弹幕翻译开关。
- 模式：流畅 / 完整 / 精准。
- 目标语言。
- 是否显示原文。
- 高频时是否启用摘要。

如果新增设置，需要改：

- `res/xml/translate_preferences.xml`
- `smali/org/chromium/chrome/browser/translate/TranslateSettings.smali`
- 可能需要新增字符串资源和 preference click listener。

## 文件改造范围

第一阶段建议只改：

- `smali/org/chromium/chrome/browser/translate/GoogleAiTranslateHelper.smali`
  - 升级 `f(String)` 注入脚本版本，例如 `version: 8`。
  - 引入批处理队列、超时 flush、有界队列、缓存上限、高峰模式。
  - 把当前逐条 `callOne()` 改为 `callBatch()`。
  - 回填方式从直接替换原文改为插入译文节点。

可选同步更新：

- `README_googleai_changes.txt`
  - 记录弹幕翻译策略和限制。
- `docs/danmaku-translation-plan.md`
  - 作为后续实现清单维护。

不建议第一阶段改：

- Chromium 原生网络栈。
- 平台 WebSocket 协议解析。
- 后端网关。
- 大量资源/设置项。

## 分阶段实施计划

### 阶段 1：批处理与限流

目标：先解决“逐条 API 跟不上”的主要风险。

任务：

- 从旧版 `b(String)` 迁移 `takeBatch()`、`callBatch()`、`parseJson()` 思路到当前 `f(String)`。
- 默认 `batchSize = 5`，`flushTimeout = 500ms`。
- 增加 `maxConcurrent = 2`。
- 增加 `requestTimeout`。
- 增加 `maxQueueSize`，队列满时丢弃低优先级旧弹幕。
- 加缓存上限和缓存命中统计。

验收：

- 低频 1 条弹幕也能在超时后翻译。
- 高频时 5 条一组发送。
- 连续 100 条模拟评论不会卡死页面。
- API 失败时页面仍可滚动和继续接收弹幕。

### 阶段 2：直播评论识别增强

目标：减少误翻页面其他内容，提高各平台兼容性。

任务：

- 抽象 `detectPlatform()`。
- 分平台维护评论容器选择器。
- 优先扫描评论容器，找不到再用启发式扫描。
- 明确排除横向飘屏弹幕、视频区域、按钮、输入框。
- 保留昵称和原文，只对消息正文做翻译。

验收：

- 抖音/快手右侧评论能持续翻译。
- 横向视频弹幕不会被误翻或遮挡。
- 页面导航后能重新注入，不重复创建 UI。

### 阶段 3：高峰模式

目标：面对 2000-5000 人直播间时不崩。

任务：

- 统计最近 5 秒弹幕速率。
- 根据速率动态切换普通/高频/极端模式。
- 添加优先级评分。
- 队列满时按优先级丢弃。
- 状态栏显示模式、队列、丢弃数量。

验收：

- 50 条/秒模拟输入时页面不明显卡顿。
- 队列不会无限增长。
- 重要问句比重复短句优先翻译。

### 阶段 4：体验和设置

目标：让用户可控。

任务：

- 增加弹幕翻译开关。
- 增加流畅/完整/精准模式。
- 支持只翻译当前直播评论，不翻译整页。
- 可选显示/隐藏原文。

验收：

- 用户能在设置中关闭弹幕翻译。
- 流畅模式明显减少 API 调用。
- 完整模式尽量翻译更多评论但仍有队列保护。

### 阶段 5：后端网关预留

目标：如果客户端直连 API 不够稳，迁移到自建网关。

网关职责：

- API Key 不下发到客户端。
- 统一批处理、缓存、限流。
- 支持多模型/多翻译服务切换。
- 返回稳定 JSON。
- 可做跨用户共享缓存。

客户端只保留：

```text
弹幕采集 -> 批处理 -> 请求网关 -> 回填
```

## 性能预算

建议以这些指标作为第一阶段调参依据：

- 普通模式首条翻译延迟：目标 0.8-2.5 秒。
- 高频模式 API 请求频率：尽量控制在 2-5 次/秒以内。
- 单批文本数量：默认 5，最高不超过 15。
- 单批字符量：建议不超过 1200-1800 字符。
- 队列长度：普通 120，高频 200。
- DOM 插入：每条最多一个译文节点，避免多层嵌套。
- MutationObserver 回调：必须 debounce，避免每个 DOM 变动都立即扫描全页。

## 风险

- 平台 DOM 经常变化，选择器会失效。
- 某些直播页 CSP/CORS 可能影响页面内 fetch。
- 直接在页面 JS 中调用 Gemini 会暴露用户 API Key 给当前页面上下文，这是现有架构风险；短期沿用，长期建议后端网关。
- 反编译 smali 中维护长 JS 字符串容易出错，后续改动需要非常小心字符串转义。
- 过度隐藏视频/音频可能影响用户想边看边翻译的场景，后续需要做成模式开关。

## 第一版实现建议

第一版只做最关键的改造：

1. 新增弹幕模式状态字段：`rateWindow`、`dropCount`、`mode`、`maxQueueSize`、`batchSize`、`flushTimeout`。
2. `enqueue()` 只负责过滤、去重、入队和调度。
3. `schedule()` 支持“满批立即发”和“超时发当前批”。
4. `process()` 控制并发，不逐条 await。
5. `callBatch()` 使用 JSON 映射回填。
6. `apply()` 插入译文节点，不替换原文。
7. `setStatus()` 展示队列、失败、丢弃、高峰模式。

这样能先解决最大的性能问题，也方便后续继续扩平台和设置项。
